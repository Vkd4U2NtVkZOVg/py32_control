## 修复：ADC EOC 超时（提交 9546521）

- `adc.c` 新增 `ADC_EOC_SPIN_LIMIT = 10000U`，替换 `adc1_convert()` 里的 1000000U。
  推导：239.5+12.5 ADC 时钟 @8 MHz ≈ 32 µs；每轮询 ~8-12 周期 ≈ 0.3 µs → 约需 100 轮，
  10000 留 ~100× 余量，最坏阻塞从 100-300 ms/通道 降到几 ms。
- 验证方式：用 python 从 adc.c 抽出 `adc1_convert` + 宏，配 LL 桩用 MSVC 编译运行，
  两条路径（EOC 正常返回 1234/ok=1；EOC 死掉返回 0/ok=0）都通过。
- 本机无 arm-none-eabi-gcc，整机编译未做。
- 结论（P2.1 电流标定缓存）：不需要每周期刷新，但 `TRES_CMD_DEFAULT_PARAMS` 是运行时
  可达路径（恢复默认后 adc 缓存仍是旧标定，tec_control 已跟进）→ 建议按
  `NvParams_GetCacheGeneration()` 失效，稳态只多一次 uint32 比较。（用户随后采纳，见 a57dec7）

## ADC 超时的完整推导（回答"算准了吗"）

- HSE=16 MHz（eide.yml:102 `HSE_VALUE=16000000U`）→ PLL 固定 ×2 → SYSCLK 32 MHz
  （rcc.c:100-103）→ AHB/APB 均 DIV1（rcc.c:107-108）→ PCLK 32 MHz
  → ADC CKMODE=PCLK/4 = **8 MHz**（adc.c:237）
- 采样 239.5 + 处理 12.5（ll_adc.h:1759，12 位）= 252 ADC 时钟 = **31.5 µs**
- 轮询一圈 ≈ 8-12 周期 @32 MHz ≈ 0.25-0.37 µs（-Og，eide.yml "level-debug"）
- 需要约 105 圈 → 10000 留 ~95× 余量；最坏墙钟 2.5-3.7 ms/通道
- **关键性质**：轮询循环和 ADC 同源于 PCLK，时钟变了圈数不变 → 余量只取决于代码形态，
  与主频无关；只有改 ADC 预分频（DIV8/16/64）才需要重算（DIV64 时需 ~1680 圈，仍有 6×）
- 旧值 1e6 ≈ 300-470 ms/通道，三通道 0.9-1.4 s ≥ 1 s 控制周期 → 保护任务直接超期
- 未验证：真实 Thumb 指令流（无 arm-none-eabi 工具链）、上板实测 APB 等待周期

## 修复：stale EOC（提交 588037b）

- `adc1_convert()` 在 StartConversion 前加 `LL_ADC_ClearFlag_EOC()`。
  EOC 由硬件锁存且 StartConversion 不清它；上次超时放弃的转换会在 32 µs 后置位，
  下次调用第一圈就退出等待并读 DR（另一个通道的结果）→ 看起来完全合理的陈旧样本。
- 验证桩按硬件语义建模（StartConversion 不清标志、完成需 N 圈）：正常 3 圈；
  入口带陈旧标志仍跑满 3 圈（不清则是 1 圈）；死 EOC 在 10001 圈超时。

## 修复 NVM_FLASH_TIMEOUT（提交 7a7c3ad）

- 从 `datasheet/PY32F030系列数据手册_V2.1.pdf` 表 5-18（第 69 页）查到实测参数：
  **t_prog 1.0 ms typ / 1.5 ms max，tERASE 3.0 ms typ / 4.5 ms max**。
- 一次 Save = 2 页擦 + 2 页编程 ≈ 12 ms 最坏；单次等待上限 4.5 ms（擦除）。
- 1e6 圈 × 0.3 µs ≈ 300 ms/次（约 50 倍余量），4 次等待全在 `__disable_irq()` 内 →
  故障路径最坏 1.2 s 全中断关闭。改为 1e5（≈30 ms，约 7 倍余量），故障路径降到 ~120 ms。
- 加 `_Static_assert(NVM_FLASH_TIMEOUT >= 30000u, ...)` 防手改；变异成 20000 会编译失败。
- 环境技巧：`pip install pypdf` 后可提取中文 PDF 文本（本机原先没有 PDF 库），
  用 `PdfReader(...).pages[i].extract_text()` 按关键词定位参数表。
